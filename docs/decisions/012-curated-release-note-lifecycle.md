# 012 — Curated in-app release-note lifecycle

## Status

Accepted

## Context

Nestra keeps a technical changelog generated by Release Please and a smaller localized summary that
the application can show offline. Assigning ordinary product work to an anticipated version made
agents guess Release Please's future result and encouraged reconstructing or correcting notes at
release time. Requiring every visible adjustment also made the summary noisy, while released copy
needed stronger protection from accidental reassignment or deletion.

## Decision

Keep one machine-readable `Unreleased` collection beside immutable released history. A curated
change uses one stable identifier, one `new` or `fixes` classification, and paired concise English
and Polish translations. Only clearly notable user outcomes are committed automatically. Borderline
copy is shown to the owner for an editorial decision, and minor or internal work has no entry.

Ordinary implementation pull requests may add to `Unreleased` but never assign a product version or
publication date. The owner-triggered Release Please preparation is the only promotion boundary. It
moves all pending identifiers into the candidate version, uses that release attempt's UTC date as
the planned publication date, and clears `Unreleased` on the candidate branch. If there are no
pending curated notes, the technical release continues without an empty in-app entry.

Promotion accepts the exact current `main` version as its baseline. It preserves all history at or
below that baseline, folds an existing pending candidate and current `Unreleased` identifiers
together without duplicates, and replaces the pending version when Release Please calculates a
different candidate. Repeating preparation for the same version keeps the original planned date
and produces the same data.

Repository validation checks versions, dates, ordering, identifiers, translation parity, concise
single-line copy, candidate cleanliness, and released-history preservation against `main`. Runtime
code reads only released entries, so pending copy cannot appear before publication and a maintenance
release cannot open an empty What's New dialog.

## Consequences

- Product work records notable copy when its context is fresh without predicting release timing.
- The owner retains final editorial control over borderline copy and over when `/release` runs.
- Release candidates receive deterministic versioned notes and can be regenerated safely.
- Technical GitHub Release notes and curated in-app notes remain separate sources with different
  audiences and levels of detail.
- Adding a curated item requires one data identifier and matching English and Polish translations.
- Released copy is intentionally difficult to edit; a verified correction requires a deliberate
  policy change rather than an incidental feature pull request.

## Alternatives considered

- Keep an anticipated version in ordinary pull requests: rejected because Release Please may later
  choose a different patch or minor version.
- Build in-app notes from `CHANGELOG.md`: rejected because technical commit history is too detailed,
  is not an offline localization source, and does not provide curated Polish copy.
- Use a remote CMS: rejected because it adds availability, security, and operational complexity for
  a small local history.
- Require a note for every visible change: rejected because minor polish obscures meaningful product
  outcomes and increases editorial overhead.
